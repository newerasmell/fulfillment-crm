# Wave 4 audit (independent auditor per track, then fixes)


## P10-01/02 Товарителници + Тикети от склада

Verdict before fixes: **PASS**

- **MEDIUM** `src/server/tickets/tickets.ts:170` — The 'unreviewed' tab filters on `reviewedAt: null`, but 'reviewed' everywhere else means `reviewedAt >= lastEventAt` (reviewedNow, line 177, and countOpenTickets). Scenario: an operator reviews a ticket, then FHB sends ticket_updated. The row shows reviewed=false and the Начало card counts it, but the Непрегледани chip and list leave it out, so the follow-up gets missed. Unreviewed CLOSED tickets are also counted there. The test at shipments.test.ts:486 only checks countOpenTickets after the newer event and never checks board.counts.unreviewed, so it would not catch this.
- **MEDIUM** `src/app/(app)/page.tsx:19` — The Начало 'Тикети' card shows open tickets not reviewed since their last event, but it links to /tickets?tab=open, which lists every open ticket, reviewed ones included. The number on the card and the list it opens do not match.
- **MEDIUM** `src/server/shipments/board.ts:261` — COD per shipment row is the order's full COD (codOf(r.order)), shown on every Fulfillment of the order. A rerouted order has a CANCELLED original shipment and a new one, and both show (and export in the cod column) the full amount. The cancelled row looks like money still to collect, and summing the CSV cod column double-counts the order. The task forbids counting cancelled shipments and double counting in money numbers.
- **MEDIUM** `src/server/shipments/board.ts:178` — The created-date filter uses UTC days (`${from}T00:00:00Z`), but the group works in Account.timezone (default Europe/Sofia, schema.prisma:176), and the table renders dates in the locale's zone. Scenario: a shipment created at 00:30 Sofia time on 3 Nov is 22:30 UTC on 2 Nov. It is missing from a from=to=2026-11-03 filter and its CSV, and appears under 2 Nov. The iso() CSV dates at board.ts:450 have the same UTC shift.
- **MEDIUM** `prisma/schema.prisma:818` — Every board load runs 9 count queries plus a page sorted by createdAt desc, and each header-search keystroke (debounced 200 ms) runs `trackingNumbers has`, `externalId contains insensitive`, and Order.number/customerName ILIKE. Fulfillment has only @@index([accountId, status]) and no GIN index on trackingNumbers, so all of these become sequential scans joined to Order on a large shipment table. Exports use 20 OFFSET pages over the same unindexed sort, which can also repeat or skip rows when new shipments arrive during the export.
- **LOW** `src/components/shell/GlobalSearch.tsx:57` — Pressing Enter uses `hits` from the previous query: hits are not tied to the text that produced them. Scenario: type '1001', wait for results, then quickly type '10015' and press Enter within 200 ms. The search opens the first hit for '1001', a different order.
- **LOW** `src/server/tickets/tickets.ts:209` — listTickets returns at most 300 rows with no paging or 'more' indicator, while the chip counts are unbounded. Above 300 tickets, the chip number and the visible rows disagree and older tickets can't be reached.
- **LOW** `src/server/shipments/shipments.test.ts:278` — The restricted-scope test covers list, detail, CSV and search for shipments. For tickets, only markTicketReviewed is tested with a restricted member. listTickets and countOpenTickets are never called with a restricted member, so a regression that drops scopeWhere from the ticket board would pass.

## P10-03/05 Офиси, PUDO, потребители + Фактури

Verdict before fixes: **PASS**

- **MEDIUM** `src/server/directory/invoices.ts:55-60, 111-146` — Invoice rows are scoped only by the FHB connection's companyId. The order each row belongs to is not checked. Routing (src/server/routing/engine.ts:302-315) can send an order of company B through company A's FHB warehouse when both are in the same product line. An OPERATOR limited to company A then sees B's per-order invoice numbers and PDF links on /invoices. The fulfillment join also hands them B's CRM order number and order id as a link. The reverse fails too: a member limited to B never sees B's own invoices. The test (directory.test.ts:321-326) only checks a member whose company owns no c
- **MEDIUM** `src/server/directory/directory.ts:275, 295-301, 458-463` — Pick-up points are listed and counted twice. FhbPickupPoint is unique per (connectionId, service, queryCountry, vendorId), and fhb/sync.ts:524-537 stores one list per queried country. A service loaded once without a country and once with `SK` therefore has the same point stored under queryCountry "" and "SK". The offices tab then shows that point twice and adds it to `total`/`totals.fhb` twice. The couriers tab doubles the 'pick-up points' count per carrier. No test covers a service loaded for two query countries.
- **MEDIUM** `src/server/directory/invoices.ts:77-109` — Every load of /invoices runs three `count` queries and one `findMany` on FhbOrderMirror, all filtered on JSON paths (`raw->invoice`, `raw->invoice_number`) and on `string_contains` against raw. No index can serve these filters. This table grows with every shipment, so each page view does four full scans that decompress the jsonb, and it gets worse with every FHB order.
- **LOW** `src/server/directory/invoices.ts:45` — The 'С PDF' filter uses `string_contains: "http"`, so any string containing 'http' counts as a PDF. A value like `javascript:alert('http')` or `see http://...` lands in the PDF tab and its count. The row itself then renders no link, because safeInvoiceUrl drops it. Counts and rows disagree. The test (SYN-4) uses `javascript:alert(1)`, which has no 'http', so it does not catch this.
- **LOW** `src/server/directory/invoices.ts:47-50 vs 30-31` — `str()` accepts a numeric invoice_number and renders it, but `hasNumber` matches only JSON strings (`string_contains`). An invoice_number sent as a JSON number is therefore excluded from every tab and from every count.
- **LOW** `src/server/directory/directory.ts:332 (FHB copy code = vendorId)` — The directory tells operators to paste the FHB point `id` into `delivery_point`. fhb-kika-v3.md:859 only says "`delivery_point`: string maxLength=255 — Delivery point code", and GET /delivery-point returns both `id: integer` and `external_code: string` (fhb-kika-v3.md:2653-2654). The reference does not say which one is expected, so the copied value may be the wrong one.
- **LOW** `docs/BACKLOG.md` — BACKLOG.md has no P10-03 or P10-05 entries, so the acceptance criteria cannot be checked and the tasks are not marked [x]. The diff also leaves PROGRESS.md unchanged, although CLAUDE.md requires updating it every task. The builder states the auditor subagent was not run before the commit.

Example: on 2026-11-03 a user picks June-August 2025. The other five reports show that period correctly. The COD report quietly shows only shipments created after 2025-11-03, so for that period it shows 0 or partial expected/received/paid/outstanding with no warning. If more than 20k rows match, the report is also cut short with no truncated flag. These are wrong mo
- **MEDIUM** `src/server/reports/orders.ts:68,105,126` — The 'Of which COD' column (codCents) is the sum of `o.total` for COD orders in the order currency. It is not the COD amount (`codAmount`/`codLocalAmount` in `codLocalCurrency`). Example: an order in EUR shipped to Hungary has its COD in HUF. It shows here as 'COD' in EUR, so the Orders report and the COD report give different COD totals for the same orders. Partly prepaid COD orders are also overstated. CLAUDE.md says COD lives in the destination country's local currency.
- **MEDIUM** `src/server/reports/reports.test.ts:158-449` — Company/line scoping for a restricted member is tested on the database only for ordersReport (activeCompanyId and lineCompanyIds=[]). The shipments, timing, review (raw-SQL findings plus the Prisma relation filters), COD and stock reports have no test that a member limited to company A cannot see company B's shipments, findings, decisions or COD amounts. companyScope (a restricted member with no active company) is tested only through the pure scopeCompanyIds. A regression in any one companySql or scopeWhere call would pass CI.
- **LOW** `src/server/reports/review.ts:63` — 'Waiting now' (open NEEDS_REVIEW/ON_HOLD/BLOCKED) is filtered by placedAt inside the period. An order placed 40 days ago that is still ON_HOLD is missing from 'Waiting now' under the default 30-day range, so the backlog figure is understated even though the label says 'now'.
- **LOW** `src/server/reports/shipments.ts:78,95` — A Fulfillment that ends CANCELLED after it shipped (shippedAt set) counts as sent but not as delivered or returned. inTransit then counts it forever, and the delivery rate is lowered.
- **LOW** `src/server/reports/review.ts (findings query, `min(x->>'message_bg') AS sample`)` — The sample finding text goes into the UI and the CSV. Some validator messages include recipient address fragments (for example eushipments/validators.ts:149, the truncated buildingNumber) or other orders' numbers (labels/manual.ts:248). The aggregate export then carries one arbitrary customer's address data.
